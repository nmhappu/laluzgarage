Build a complete native Android application in Kotlin using Jetpack Compose, matching the existing workshop management app as closely as possible in UI, layout, flow, hierarchy, interaction patterns, and visual language. The goal is to reproduce the same product model and interface structure, but replace the database with a custom repository/data layer.

This is not a new app idea. It is a clone of the same business workflow, optimized for Android native UI, with the storage system changed.

Core requirement:
- Keep the same exact app behavior and UI model as the original product.
- Only change the database/backend layer.
- The UI must remain functionally and visually equivalent to the original app even if the backend is a local database, Room, in-memory repository, or a custom API-backed repository.

Technology stack:
- Kotlin
- Jetpack Compose
- Material 3
- Compose Navigation
- ViewModel + StateFlow or MutableStateFlow
- Repository pattern
- Room optional if preferred, but not mandatory
- Local mock data or SQLite-backed repository acceptable for the initial version
- Clean architecture structure preferred:
  - ui/
  - viewmodel/
  - repository/
  - data/
  - domain/
  - model/
  - theme/
  - navigation/

Project purpose:
Create a workshop operations dashboard for managing:
- customers
- vehicles
- service records
- inventory / spare parts
- technician/advisor users
- work orders / repair jobs
- vehicle intake workflow
- status tracking and search/filtering

The app should feel like a polished mobile-first workshop management dashboard, with a desktop/tablet-friendly sidebar layout when width permits.

  - muted text: #94A3B8
  - primary accent green: #10B981
  - secondary blue: #3B82F6
  - warning amber: #FBBF24

- Light mode variant should exist, but dark theme is default
- Use clear spacing, bold typography, subtle shadows, and minimal but present motion
- Use compact but strong information hierarchy
- Respect mobile sizes while still supporting tablet/desktop layout

The app should use:
- bold uppercase labels

11. Repository pattern
Absolutely critical:
- The UI must not depend on Firebase or any specific database.
- Create repository interfaces such as:
  - CustomerRepository
  - VehicleRepository
  - PartRepository
  - ServiceRecordRepository
  - UserRepository
- Use a data layer abstraction so the UI can be switched between implementations:
  - Local/mock repository
  - Room database repository
  - SQLite repository
  - remote API repository
- The app should run with a seeded/local mock repository by default
